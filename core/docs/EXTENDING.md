# Extending

TicketFlow is meant to be adapted. Your team has its own conventions, review lenses and domain knowledge, and there is a place for
each of them that survives every update. The one rule: add, never edit what TicketFlow manages.

What is yours and what is TicketFlow's: `sync` rewrites the runtime, the stubs and the managed blocks of generated files, and never
touches the places below. Add to TicketFlow here; never edit a managed file.

## `.ticketflow/custom/`

A file here adds to and overrides the TicketFlow file of the same name; each canonical skill and role starts by reading its own.

| File | Extends |
|---|---|
| `implement-ticket.md` | the implement-ticket skill: your build, test and live-check commands |
| `post-merge.md` | the steps after a merge: deploy, smoke checks, your handoff rules |
| `create-ticket.md` | the create-ticket skill: your label and tracker conventions |
| `engineering-method.md` | the engineering-method skill, ticket or not: your test, review and lean-code conventions |
| `orchestrate-tickets.md` | the optional multi-ticket skill: your budget and parallelism defaults, tickets that must never run together |
| `ticket-planner.md`, `pr-reviewer.md`, `e2e-verifier.md` | that role: the guides to read, your lenses, your accounts and viewports |
| `<practice>.md` | one enabled practice (its README says what to record) |
| `labels.json` | labels beyond TicketFlow's (same format as `templates/labels.json`); `labels sync` adds them |

Keep each file short: it is read every time its skill or role runs.

## Testing a rule you add

A rule costs tokens on every run, so keep it only if it changes what the agent does. Write down the situation that breaks without it
(for example, a bug fix that patches the symptom). Run that situation once without the rule and once with it, in a scratch repo and
with the same agent and model. If the behaviour is the same, delete the rule; if it changed, keep it and note the situation in the
file.

## AGENTS.md

`render` owns only the block between `ticketflow:begin agents` and `ticketflow:end agents`. Everything else in the file is yours. Put
a **Review Guidelines** section there: every reviewer applies it (the AGENTS block says so).
Rules that apply to every ticket belong in AGENTS.md; rules that change how one skill or role works belong in `custom/`.

## Your own skills

Skills and agents you add under `.claude/skills/`, `.claude/agents/`, `.agents/skills/`, `.codex/agents/`, `.cursor/agents/`, `.gemini/agents/`, `.opencode/agents/` or `.github/agents/` with other names are
untouched. A file you wrote at a path where TicketFlow generates a stub (no `Generated by ticketflow gen-stubs` marker) is a
conflict: `gen-stubs` writes nothing and exits 1. Move what is repo-specific to `custom/<name>.md` and delete the old file.
**Do not shadow a TicketFlow skill or role with your own copy**: it stops following upgrades. Put the difference in `custom/<name>.md`.

## Domain guides

Product rules live in short guides at `docs/agents/<name>.md`, each with a `paths:` list in its frontmatter. They are your content,
never TicketFlow's. With the `domain-guides` practice, `gen-stubs` turns each guide into a Claude rule file under `.claude/rules/`
and the AGENTS block tells other agents to read the guides whose paths match.

## Practices

Ten optional practices ship in `practices/`: `live-verify`, `runtime-settings`, `i18n`, `database`, `provider-adapters`,
`api-endpoints`, `ui-screens`, `domain-guides`, `deploy-gating`, `analytics-events`. Enable one by naming it in `practices` in the
config, then `sync`: its folder is copied to `.ticketflow/practices/<name>/`, its skill (if any) gets a stub, and its one-line rules
reach the AGENTS block and the PR template. `live-verify` also needs `live_verify_skill: "live-verify"`, which gives the
`e2e-verifier` role its stub. Each practice's README says what it adds and what to record in `custom/<practice>.md`. They are
rules and checklists, not code.
